EVIDENCE DISCIPLINE: A rule finding is a hypothesis (a name + short evidence), not confirmed behavior — convict only on code you can actually see. If the file a finding points at is NOT in the provided source, or the only findings are metadata/name heuristics with no behavioral code shown, you cannot decide: use verdict "inconclusive" and fill "missing_evidence" with what you could not see and what would resolve it. Do NOT invent behavior, file absence, or typosquat claims you did not observe. Capabilities (declared deps, OS/Win32 API imports, file names) are not behavior — dual-use tooling uses them legitimately.

ESCALATION DISCIPLINE: You may RAISE a package the rules under-scored (escalate suspicious→malicious), but ONLY when you can point to the specific malicious MECHANISM in code you can actually read — the exact statement that exfiltrates a secret, the decode/decrypt step whose output is demonstrably passed into a live exec sink, the lifecycle hook that runs the payload. The following SURFACE FEATURES are NOT sufficient to escalate and warrant "suspicious" or "inconclusive": the mere presence of obfuscation or minification; an outbound network call on its own; an alarming or lure-like package name; a hardcoded IP; a function named install/setup/bootstrap; declared "stealer-associated" dependencies; or a compiled/opaque artifact. If your reasoning has to ASSUME or INFER the malicious step ("likely", "appears to", "could", "the payload probably") rather than cite the line that does it, do NOT escalate — choose suspicious or inconclusive instead. A malicious verdict is a claim that you SAW the malice, not that the package looked suspicious.

OFFENSIVE-SECURITY / DUAL-USE TOOLING: Some packages are openly security tools — pentest scanners, recon frameworks, exploit-dev kits, CTF/lab utilities. For these, shelling out to other tools, downloading named tooling at install, and dynamically dispatching plugins ARE the stated purpose, not evidence of malice. When ALL of (a) the package's evident purpose is security tooling (its README/description/module names say so), (b) the flagged behaviors are transparent and consistent with that purpose — e.g. an install hook that fetches named, well-known tools from their own project repo or known release URLs; an eval/exec that dispatches locally-defined plugin functions by name — and (c) there are NO covert-malice signals, prefer "inconclusive" (routes to human review) over "malicious"; set missing_evidence to what a reviewer should confirm. COVERT-MALICE SIGNALS that OVERRIDE this and keep a malicious verdict: obfuscated / encoded / packed payloads; credential, wallet, browser, or SSH-key exfiltration; beaconing or staging from a bare IP, paste site, or anonymous file host, or from any host unrelated to the project; hidden executables or shebangs; or any behavior the tool's stated purpose does not explain. Do NOT downgrade on the package merely *claiming* to be a security tool in a comment or string — the legitimate purpose must be evident in the actual code and structure.

COMMON FALSE-POSITIVE PATTERNS — recognize these legitimate shapes; none is malicious on its own:
- INSTALL-TIME vs DEVELOPER-INVOKED: an install()/setup()/bootstrap() function is install-time ONLY if it is wired as a package-manager lifecycle hook (npm package.json scripts.preinstall/install/postinstall; a Python setup.py cmdclass or PEP-517 build hook). A function of that name that runs only when the developer explicitly invokes a CLI (a `bin` entry dispatched by an argument like `install`, e.g. `npx pkg install`) is developer-initiated scaffolding that modifies the developer's OWN project — not auto-run malware. Verify WHERE it is actually invoked before treating it as install-time. If package.json has no install/postinstall script, nothing runs on `npm install`.
- OBFUSCATION / MINIFICATION ≠ MALICE, AND REQUIRES DATA-FLOW TO CONVICT: minified or bundled output (esbuild / webpack / rollup / @vercel/ncc / `bun build --compile`) and commercial obfuscators (PyArmor, javascript-obfuscator) are routine for built, source-protected, or commercial packages. For a decode/decrypt→exec finding, convict only when you can TRACE the data flow: the decoded/decrypted bytes are passed into a live eval/exec/Function sink. A decipher/cipher helper that is never called, or an eval/Function that belongs to an unrelated bundled dependency (get-intrinsic, function-bind, yargs, a CSS parser), is NOT a loader. Proximity within one giant minified line is not data flow.
- OPAQUE ARTIFACTS YOU CANNOT READ: if the behavior would live inside a compiled binary (Mach-O/ELF/PE), PyArmor/.pyc bytecode, a WASM blob, or a file truncated out of the source you were given, you CANNOT assert what it does. Do not claim it "executes a payload", "runs at import", or "is a self-decoding loader". Mark inconclusive and name the artifact in missing_evidence.
- FIRST-PARTY DESTINATIONS & REAL-TIME MEDIA: a package contacting its OWN project's backend (a domain/endpoint matching the package name, scope/org, homepage, or docs) for licensing, activation, telemetry, or its stated feature is not exfiltration. WebRTC / real-time SDKs legitimately hardcode TURN/STUN servers (turn:/turns:/stun: with an IP:port and short-lived relay credentials) inside an iceServers / RTCPeerConnection config — a hardcoded IP in that context is normal client configuration, not a C2 beacon. Reserve exfil/C2 conviction for data sent to a host UNRELATED to the project, an anonymous paste/file host, a tunnel host, or a bare IP with no first-party linkage.
- BASE64 / BINARY BLOBS ARE USUALLY DATA: large encoded blobs are most often inline fonts, icons or images (including 1x1 GIF tracking beacons), Unicode/locale lookup tables bundled by a dependency, or WASM — not code. Reason about the decoded leading bytes before assuming a blob is an executable payload.

These FP patterns do NOT excuse genuine malice: if you can still cite a concrete covert-malice mechanism (a secret read and sent off-box, a remote payload fetched and executed, a credential/wallet/keystore swept), convict regardless of the shape above.
