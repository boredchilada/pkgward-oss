TWO-AXIS JUDGMENT — decide these two SEPARATELY before you pick a verdict. Most false alarms come from collapsing them: a package that DOES alarming things is not the same as a package that INTENDS harm. Rate each axis only on code you can actually read.

  behavior_risk  = how dangerous is what the code DOES, independent of intent:
    none   — no exec sinks, no outbound network, no secret/credential access.
    low    — ordinary app behavior (a single first-party network call, config reads).
    medium — install-time code, dynamic dispatch, outbound egress, or obfuscation/minification — each individually explainable.
    high   — multiple of: a live eval/exec sink reachable from decoded/decrypted bytes; install-time auto-exec (a real lifecycle hook); credential/keystore/wallet/browser access; a self-decoding loader; a hidden executable/shebang.

  malicious_intent = is there CONCRETE evidence the intent/target is hostile (a line you can cite, not an inference):
    none    — every flagged behavior is explained by the package's evident, legitimate purpose; destinations are first-party.
    unclear — the deciding code is obfuscated, compiled, opaque, or truncated out of what you were shown — you cannot read the intent.
    evident — you can point to the exact malicious MECHANISM: a secret read and sent to a host UNRELATED to the project (a bare IP, paste/file host, tunnel host, or attacker domain); a remote payload fetched and passed into a live exec sink; a credential/wallet/keystore sweep; a backdoor or C2 beacon; a hidden executable. "evident" REQUIRES the cited statement — never "likely / appears to / could / probably".

DERIVE THE VERDICT FROM THE TWO AXES:
  - malicious_intent = evident                                   -> "malicious"   (you SAW the malice; list the mechanism + IOCs)
  - malicious_intent != evident AND behavior_risk = high         -> "suspicious"  (RISKY: concerning/dual-use behavior, NO proof of malice — routes to human review, NOT an alarm)
  - malicious_intent != evident AND behavior_risk = medium       -> "suspicious"  (unless every behavior is fully first-party/explained, then "benign")
  - malicious_intent = none AND behavior_risk in {{none, low}}     -> "benign"
  - the deciding code/artifact is opaque or absent (intent unclear AND you cannot read the mechanism) -> "inconclusive" (fill missing_evidence)
A "malicious" verdict is a claim that you SAW the malice, not that the package looked dangerous. High behavior_risk alone is the "suspicious" bucket — it is the whole point of having two axes. Never emit "malicious" with malicious_intent != evident.

EVIDENCE DISCIPLINE: A rule finding is a hypothesis (a name + short evidence), not confirmed behavior — convict only on code you can actually see. If the file a finding points at is NOT in the provided source, or the only findings are metadata/name heuristics with no behavioral code shown, set malicious_intent=unclear and use verdict "inconclusive" with "missing_evidence" naming what you could not see. Do NOT invent behavior, file absence, or typosquat claims you did not observe. Capabilities (declared deps, OS/Win32 API imports, file names) are not behavior — dual-use tooling uses them legitimately.

ESCALATION DISCIPLINE: You may RAISE a package the rules under-scored, but malicious_intent=evident requires the specific mechanism in code you can actually read — the exact statement that exfiltrates a secret, the decode/decrypt step whose output is demonstrably passed into a live exec sink, the lifecycle hook that runs the payload. These SURFACE FEATURES set behavior_risk but DO NOT establish intent, so they cannot yield "malicious": the mere presence of obfuscation or minification; an outbound network call on its own; an alarming or lure-like package name; a hardcoded IP; a function named install/setup/bootstrap; declared "stealer-associated" dependencies; or a compiled/opaque artifact. If your reasoning has to ASSUME or INFER the malicious step, malicious_intent is at most "unclear" — choose suspicious or inconclusive.

OFFENSIVE-SECURITY / DUAL-USE TOOLING: Some packages are openly security tools — pentest scanners, recon frameworks, exploit-dev kits, CTF/lab utilities. For these, shelling out to other tools, downloading named tooling at install, and dynamically dispatching plugins ARE the stated purpose: that is high behavior_risk with malicious_intent=none, i.e. "suspicious" (human review), NOT "malicious". This holds when ALL of (a) the package's evident purpose is security tooling (its README/description/module names say so), (b) the flagged behaviors are transparent and consistent with that purpose, and (c) there are NO covert-malice signals. COVERT-MALICE SIGNALS that flip malicious_intent to evident: obfuscated / encoded / packed payloads reaching an exec sink; credential, wallet, browser, or SSH-key exfiltration; beaconing or staging from a bare IP, paste site, or anonymous file host, or any host unrelated to the project; hidden executables or shebangs; or any behavior the tool's stated purpose does not explain. Do NOT downgrade on the package merely *claiming* to be a security tool in a comment or string — the legitimate purpose must be evident in the actual code and structure.

COMMON FALSE-POSITIVE PATTERNS — these are high-behavior_risk-but-benign shapes; none establishes malicious intent on its own:
- INSTALL-TIME vs DEVELOPER-INVOKED: an install()/setup()/bootstrap() function is install-time ONLY if it is wired as a package-manager lifecycle hook (npm package.json scripts.preinstall/install/postinstall; a Python setup.py cmdclass or PEP-517 build hook). A function of that name dispatched only when the developer runs a CLI (a `bin` entry, e.g. `npx pkg install`) is developer-initiated scaffolding — behavior_risk medium, intent none. If package.json has no install/postinstall script, nothing runs on `npm install`.
- OBFUSCATION / MINIFICATION ≠ MALICE, AND REQUIRES DATA-FLOW TO CONVICT: minified/bundled output (esbuild / webpack / rollup / @vercel/ncc / `bun build --compile`) and commercial obfuscators (PyArmor, javascript-obfuscator) are routine for built or commercial packages. For a decode/decrypt→exec finding, malicious_intent is evident ONLY when you can TRACE the data flow: the decoded bytes are passed into a live eval/exec/Function sink. A decipher helper that is never called, or an eval/Function belonging to an unrelated bundled dependency (get-intrinsic, function-bind, yargs, a CSS parser), is NOT a loader. Proximity within one giant minified line is not data flow.
- OPAQUE ARTIFACTS YOU CANNOT READ: if the behavior would live inside a compiled binary (Mach-O/ELF/PE), PyArmor/.pyc bytecode, a WASM blob, or a file truncated out of the source, you CANNOT assert what it does — malicious_intent=unclear, verdict "inconclusive", name the artifact in missing_evidence. Do not claim it "executes a payload" or "is a self-decoding loader".
- FIRST-PARTY DESTINATIONS & REAL-TIME MEDIA: a package contacting its OWN project's backend (a domain/endpoint matching the package name, scope/org, homepage, or docs) for licensing, activation, telemetry, or its stated feature is not exfiltration (intent none). WebRTC / real-time SDKs legitimately hardcode TURN/STUN servers (turn:/turns:/stun: with an IP:port and short-lived relay credentials) inside an iceServers / RTCPeerConnection config — a hardcoded IP there is normal client config, not C2. Reserve exfil/C2 (intent evident) for data sent to a host UNRELATED to the project, an anonymous paste/file host, a tunnel host, or a bare IP with no first-party linkage.
- BASE64 / BINARY BLOBS ARE USUALLY DATA: large encoded blobs are most often inline fonts, icons or images (including 1x1 GIF tracking beacons), Unicode/locale tables bundled by a dependency, or WASM — not code. Reason about the decoded leading bytes before assuming a blob is an executable payload.

These FP patterns do NOT excuse genuine malice: if you can still cite a concrete covert-malice mechanism (a secret read and sent off-box, a remote payload fetched and executed, a credential/wallet/keystore swept), malicious_intent is evident and you convict regardless of the shape above.
